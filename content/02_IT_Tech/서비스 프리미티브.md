# 서비스 프리미티브 (Service Primitive)

---

## I. 계층 간 통신의 추상화, 서비스 프리미티브의 개요

### 가. 서비스 프리미티브의 정의

* OSI 참조 모델에서 인접한 계층 간(N+1계층과 N계층) 서비스를 요청하고 제공받기 위해 SAP(Service Access Point)를 통해 교환하는 추상적인 상호작용 명령어(연산 단위)

### 나. 서비스 프리미티브의 필요성 및 특징

* **[[모듈화]] 및 독립성**: 각 계층의 내부 구현을 숨기고, 표준화된 인터페이스(명령어)만 제공하여 [[프로토콜]] 변경에 따른 타 계층 영향 최소화
* **[[추상화]] 제공**: 동위 계층 간의 물리적/논리적 통신(PDU 교환)을 인접 계층 간의 추상적 상호작용으로 [[캡슐화]]
* **4대 기본 연산**: 요청(Request), 지시(Indication), 응답(Response), 확인(Confirm)의 4가지 형태로 구성

---

## II. 서비스 프리미티브의 개념도 및 핵심 기술 요소

### 가. 서비스 프리미티브의 동작 원리 및 개념도

```mermaid
flowchart LR
    subgraph Sender ["발신측 (N+1 계층) / Service User"]
        Req["1. Request (요청)"]
        Conf["4. Confirm (확인)"]
    end

    subgraph Network ["서비스 제공자 (N 계층) / Service Provider"]
        SAP1((SAP))
        SAP2((SAP))
        
        SAP1 <== "동위 계층 간 프로토콜 통신 (PDU 교환)" === SAP2
    end

    subgraph Receiver ["수신측 (N+1 계층) / Service User"]
        Ind["2. Indication (지시)"]
        Res["3. Response (응답)"]
    end

    Req -->|서비스 호출| SAP1
    SAP1 -.->|결과 통보| Conf

    SAP2 -.->|이벤트 알림| Ind
    Res -->|결과 반환| SAP2
    
    classDef layer fill:#f9f9f9,stroke:#333,stroke-width:2px;
    classDef sap fill:#e2efda,stroke:#548235,stroke-width:2px;
    class Sender,Receiver,Network layer;
    class SAP1,SAP2 sap;

```

* 발신측 N+1계층이 Request로 서비스를 요청하면, N계층(Provider)을 거쳐 수신측에 Indication으로 알림을 전달함
* 수신측 N+1계층이 Response로 응답하면, 다시 N계층을 거쳐 발신측에 Confirm으로 최종 처리 결과를 확인함

### 나. 서비스 프리미티브의 핵심 구성 요소

| 구분 | 요소기술(키워드) | 세부 설명 |
| --- | --- | --- |
| **기본 연산(발신)** | Request (요청) | N+1계층이 N계층에게 특정 통신 기능(연결, 데이터 전송 등)의 수행을 요구하는 프리미티브 |
| **기본 연산(수신)** | Indication (지시) | N계층이 수신측 N+1계층에게 상대방의 요청이나 네트워크 내부의 중요 이벤트 발생을 알림 |
| **기본 연산(수신)** | Response (응답) | 수신측 N+1계층이 Indication에 대한 수락, 거절 등의 처리 결과를 N계층에 반환 |
| **기본 연산(발신)** | Confirm (확인) | N계층이 발신측 N+1계층에게 최초 Request에 대한 최종 실행 결과(성공/실패)를 통보 |
| **접근 지점** | SAP (Service Access Point) | 인접 계층 간 서비스 프리미티브와 데이터가 교환되는 논리적 접속점(인터페이스) |
| **전달 데이터** | SDU (Service Data Unit) | 프리미티브의 매개변수(Parameter)로 인접 계층 간 전달되는 순수 사용자 데이터 단위 |
| **통신 데이터** | PDU (Protocol Data Unit) | N계층이 N+1계층의 SDU에 제어 정보(PCI)를 덧붙여 동위 계층 간 교환하는 데이터 단위 |
| **제어 정보** | PCI (Protocol Control Info.) | 헤더(Header) 형태로 덧붙여지는 발신/수신 주소, 오류 제어 등의 프로토콜 제어 정보 |

## III. 서비스 프리미티브의 적용 방식 비교 및 통신 동향

### 가. 확인형 서비스(Confirmed) vs 비확인형 서비스(Unconfirmed) 비교

| 비교 항목 | 확인형 서비스 (Confirmed Service) | 비확인형 서비스 (Unconfirmed Service) |
| --- | --- | --- |
| **사용 프리미티브** | Request, Indication, Response, Confirm (4개 모두) | Request, Indication (2개만 사용) |
| **동작 특징** | 발신측이 요청 후 수신측의 최종 응답(Confirm)까지 대기 | 발신측이 요청만 하고 수신측의 응답을 기다리지 않음 |
| **[[신뢰성]] / 속도** | 신뢰성 높음 / 오버헤드 발생 및 속도 느림 | 신뢰성 낮음 / 오버헤드 적고 전송 속도 빠름 |
| **적용 프로토콜** | [[TCP]] (Transmission Control Protocol), X.25 | UDP (User Datagram Protocol) |
| **주요 활용처** | 파일 전송(FTP), 이메일(SMTP), 웹 통신(HTTP) | 실시간 스트리밍(VoIP), 단순 상태 정보 전송(SNMP) |

### 나. 계층 간 통신 추상화 기술의 향후 전망

* **OSI 참조 모델에서 마이크로서비스 API로의 진화**: 전통적인 4대 프리미티브 사상은 현대 [[MSA (Micro Service Architecture)|MSA]](Microservices Architecture) 환경에서 RESTful API(GET, POST, PUT, DELETE)의 요청-응답 모델 설계의 이론적 근간으로 계승됨
* **비동기 메시징의 확대**: 단순한 Request-Confirm 구조를 넘어, 이벤트 주도 아키텍처([[EDA]]) 기반의 Pub/Sub 모델 및 gRPC (비동기 스트리밍) 형태로 진화하며 시스템 간 결합도를 더욱 낮추는 방향으로 발전 중
