# 소프트웨어 아키텍처 평가 (Software Architecture Evaluation)

---

## I. 품질 목표 달성과 리스크 조기 식별, SW 아키텍처 평가의 개요

### 가. SW 아키텍처 평가의 정의

- 설계된 [[소프트웨어 아키텍처]]가 이해관계자의 비즈니스 목표와 **품질 속성(성능·보안·가용성·변경 용이성 등)** 을 충족하는지 분석하고, 위험 요소를 조기에 식별하는 공학적 검증 활동

### 나. 필요성

| 구분 | 내용 |
| --- | --- |
| 재작업 비용 절감 | 운영 단계의 아키텍처 변경 비용을 설계 단계에서 예방 |
| 상충관계 해결 | 보안·성능·[[HA(High Availability)\|가용성]] 등 충돌하는 품질 속성 간 균형점 도출 |
| 이해관계자 합의 | 시나리오 기반으로 기대 수준을 조율하는 공통 기준 제공 |

---

## II. SW 아키텍처 평가 절차 및 핵심 요소

### 가. ATAM 기반 평가 절차

```mermaid
flowchart LR
    REQ["비즈니스 목표 /<br/>품질 요구사항"] --> P1["1. 비즈니스 드라이버<br/>· 이해관계자 파악"]
    P1 --> P2["2. 품질 속성 시나리오<br/>(Utility Tree)"]
    P2 --> P3["3. 아키텍처<br/>접근법 분석"]
    P3 --> P4["4. 민감점 · 상충점<br/>· 리스크 식별"]
    P4 --> OUT["5. 개선안 /<br/>리스크 완화 전략"]
```

### 나. 평가 방법론

| 기법 | 핵심 관점 | 특징 |
| --- | --- | --- |
| [[SAAM]] | 변경 용이성(Modifiability) | 최초의 시나리오 기반 평가 기법 |
| [[ATAM]] | 품질 속성 간 상충관계 | SAAM 발전형, SEI 표준 평가 기법 |
| [[CBAM]] | 비용 대비 편익(ROI) | ATAM 결과의 대안을 경제성 관점에서 선택 |
| [[ARID]] | 부분 설계 검토 | 설계 완료 전 특정 컴포넌트를 사전 검토 |

### 다. 평가 핵심 개념

| 개념 | 설명 |
| --- | --- |
| 품질 속성 시나리오 | 자극(Stimulus)·환경·반응(Response) 형태로 비기능 요구를 정량화 ([[소프트웨어 품질 속성 시나리오]]) |
| [[유틸리티 트리]] | 품질 속성을 트리로 구조화하고 중요도·난이도(H/M/L) 부여 |
| 민감점 (Sensitivity Point) | 특정 품질 속성에 결정적 영향을 주는 설계 결정 (예: [[암호화]] 수준) |
| 상충점 (Trade-off Point) | 둘 이상의 품질 속성에 상반된 영향을 주는 설계 결정 |
| 품질 모델 | [[ISO IEC 25010 2023\|ISO/IEC 25010]] 품질 특성을 평가 기준으로 활용 |

## III. 평가 기법 비교 및 최신 동향

### 가. ATAM vs CBAM

| 비교 항목 | ATAM | CBAM |
| --- | --- | --- |
| 목적 | 품질 속성 충족 여부·상충관계 식별 | 설계 대안의 경제성 분석 |
| 관점 | 기술적 관점 | 비즈니스·재무 관점 |
| 산출물 | 위험, 비위험, 민감점, 상충점 | 대안별 비용·편익, ROI |
| 수행 순서 | 선행 | ATAM 이후 후행 |

### 나. 수동 평가 vs 자동화 평가

| 비교 항목 | 전통적 수동 평가 | 자동화·AI 기반 평가 |
| --- | --- | --- |
| 수행 주체 | 전문가·이해관계자 워크숍 | CI/CD 파이프라인, 정적 분석, LLM |
| 주기 | 마일스톤 시점의 일회성 평가 | 커밋·빌드 시점의 상시 검증 |
| 장단점 | 심층적 트레이드오프 논의 / 시간·비용 과다 | 빠른 피드백·드리프트 방지 / 비즈니스 맥락 이해 한계 |
| 적합 환경 | 대규모 설계 초기 | [[MSA (Micro Service Architecture)\|MSA]], [[클라우드 네이티브]] |

### 다. 최신 동향

- **피트니스 함수(Fitness Function)**: 진화적 아키텍처에서 성능·보안 지표를 코드로 정의해 파이프라인에서 자동 평가
- **아키텍처 드리프트 방지**: ArchUnit 등으로 설계 의도와 구현 간 괴리를 상시 탐지
- **Well-Architected Framework**: [[CSP]]가 제시한 보안·안정성·성능·비용·운영 원칙(Pillar)으로 클라우드 아키텍처 진단
