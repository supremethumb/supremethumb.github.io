# 릴리즈 엔지니어링 (Release Engineering)

---

## I. 재현 가능한 빌드와 안전한 출시, 릴리즈 엔지니어링의 개요

### 가. 정의

- 소스 코드가 **재현 가능한 빌드·패키징·버전 관리·배포 절차를 거쳐 사용자에게 안정적으로 전달되도록 하는** 소프트웨어 공학 분야

### 나. 필요성 및 특징

| 구분 | 내용 |
| --- | --- |
| 등장 배경 | [[MSA (Micro Service Architecture)\|MSA]]·잦은 배포로 출시 복잡도 증가, 환경 불일치(Configuration Drift) |
| 재현성 | 같은 소스·설정이면 언제나 같은 결과물 (Hermetic Build) |
| 추적성 | 결과물에서 소스 커밋·빌드 환경까지 역추적 |
| 자동화 · 정책 | 셀프서비스 파이프라인, 승인·서명 등 정책 강제 |

---

## II. 릴리스 흐름 및 구성요소

### 가. 릴리스 흐름

```mermaid
flowchart LR
    C["커밋 · 릴리스 브랜치"] --> B["격리 빌드 · 테스트"]
    B --> S["정적 분석 · 의존성 검사"]
    S --> A[("아티팩트 저장소<br/>불변 · 서명")]
    A --> D["단계적 배포<br/>(Canary · Blue-Green)"]
    D --> M["모니터링"]
    M -. "이상 시 롤백" .-> D
```

- 버전이 붙은 소스에서 격리된 빌드로 불변 아티팩트를 만들고, 서명·저장 후 단계적으로 배포하며 문제 시 이전 버전으로 롤백

### 나. 구성요소

| 구분 | 요소 | 설명 |
| --- | --- | --- |
| 버전 관리 | 브랜치 전략 | Git Flow, Trunk-based 등 릴리스 브랜치 운영 |
| | 버전 체계 | Semantic Versioning (MAJOR.MINOR.PATCH) |
| 빌드 | 격리 · 재현 빌드 | 의존성 버전 고정, 빌드 환경 컨테이너화 |
| 저장 | 아티팩트 저장소 | 바이너리·[[컨테이너]] 이미지를 불변으로 보관 (Nexus, Harbor) |
| 무결성 | 서명 · 출처 증명 | 아티팩트 서명(Sigstore), 빌드 출처(SLSA), [[SBOM]] 생성 |
| 환경 | IaC | 인프라·설정을 코드로 관리해 환경 일치 |
| 배포 | [[무중단 배포]] 전략 | Blue-Green, Canary, Rolling, 기능 토글 |
| 품질 · 보안 | [[DevSecOps]] | [[SAST]]·SCA를 파이프라인에 통합 |

---

## III. 비교 및 동향

### 가. 릴리즈 엔지니어링 vs DevOps

| 비교 항목 | 릴리즈 엔지니어링 | [[DevOps\|DevOps]] |
| --- | --- | --- |
| 초점 | 빌드·패키징·배포의 기술적 완성도 | 개발·운영 협업 문화와 흐름 전체 |
| 관심사 | 재현성, 버전, 아티팩트, 배포 전략 | 협업, 측정, 가치 흐름, 피드백 |
| 주체 | 릴리스 엔지니어, 빌드·플랫폼 팀 | 개발·운영·QA 전 구성원 |
| 관계 | DevOps를 실현하는 핵심 실천 영역 | 릴리즈 엔지니어링을 포괄하는 상위 개념 |

### 나. 동향

- Log4j·SolarWinds 사태 이후 SLSA·Sigstore 등 공급망 무결성(서명·출처 증명) 강화
- Git 상태를 배포 기준으로 삼는 GitOps와 자동 카나리 분석·자동 롤백 확산
- 내부 개발자 플랫폼으로 릴리스 파이프라인을 셀프서비스화
