# 증분형 개발 모델 (Incremental Model)

---

## I. 기능 단위 단계적 인도, 증분형 개발 모델의 개요

### 가. 정의

- 전체 요구사항을 **기능 단위 증분(Increment)으로 나누고, 증분마다 설계·구현·테스트를 거쳐 동작하는 제품을 단계적으로 인도**하는 [[SDLC]] 모델

### 나. 특징

| 구분 | 내용 |
| --- | --- |
| 등장 배경 | [[워터폴\|폭포수]]의 일괄(Big-Bang) 통합에 따른 납기 지연·후반 리스크 집중 극복 |
| 단계적 인도 | 증분마다 동작하는 SW를 인도해 Time-to-Market 단축 |
| 선형 모델의 중첩 | 증분 내부는 폭포수처럼 순차 수행, 증분 간 병렬 개발 가능 |
| 기반 아키텍처 의존 | 후속 증분 결합을 위해 초기에 견고한 기반 구조 필요 |

---

## II. 수행 절차 및 구성요소

### 가. 수행 절차

```mermaid
flowchart LR
    REQ["전체 요구사항 정의<br/>· 증분 할당"] --> ARCH["기반 아키텍처 수립"]
    ARCH --> I1["증분 1 (핵심 기능)<br/>설계 · 구현 · 테스트"]
    I1 --> R1["릴리스 1"]
    R1 --> I2["증분 2 (기능 확장)<br/>설계 · 구현 · 회귀 테스트"]
    I2 --> R2["릴리스 2"]
    R2 --> IN["증분 N<br/>시스템 · 인수 테스트"]
    IN --> RN["최종 릴리스"]
```

- 요구사항을 먼저 확정해 증분별로 배정하고, 핵심 기능부터 차례로 개발해 기존 릴리스에 통합

### 나. 구성요소

| 구분 | 요소 | 설명 |
| --- | --- | --- |
| 계획 | 기능 분할 · 우선순위 | 요구사항을 독립 통합 가능한 증분으로 나누고 가치·위험 순으로 배치 |
| 아키텍처 | 기반 아키텍처 | 증분이 누적돼도 구조가 무너지지 않도록 확장성 확보 |
| | 인터페이스 계약 | 증분·팀 간 결합도를 낮추는 API 규격 |
| 인도 | 단계적 인도 | 증분마다 고객이 검증·활용 가능한 제품 인도 |
| 검증 | [[리그레션 테스트\|회귀 테스트]] | 신규 증분이 기존 기능에 미치는 부작용 검증 |
| 통합 | 지속적 통합 | 자동 빌드·[[단위 테스트]]·[[형상 관리]]로 병합 충돌 조기 해소 |
| 릴리스 제어 | 기능 토글 | 미완성 증분의 노출을 런타임에 제어 |

---

## III. 비교 및 동향

### 가. 폭포수 vs 증분형 vs 진화형

| 비교 항목 | [[워터폴\|폭포수]] | 증분형 | [[진화형 개발 모델\|진화형]] |
| --- | --- | --- | --- |
| 개념 | 전체 단계 일괄 순차 진행 | 기능 단위로 나눠 차례로 추가 | 핵심 시스템을 만들고 피드백으로 고도화 |
| 요구사항 | 초기 확정 | 초기 확정 후 증분별 배정 | 초기 불명확, 반복하며 정제 |
| 인도 | 최종 1회 | 증분별 다회 | 버전별 다회 |
| 성장 방향 | - | 범위 확장 (수평) | 완성도 심화 (수직) |
| 약점 | 변경 수용 곤란 | 증분 통합 비용, 아키텍처 침식 | 범위 통제 곤란 (Scope Creep) |

### 나. 동향

- [[SCRUM|스크럼]] 스프린트와 CI/CD 지속 배포로 증분 단위가 더 작아짐
- [[MSA (Micro Service Architecture)|MSA]]·[[DDD (Domain Driven Design)|DDD]]로 서비스 단위 독립 증분 배포, 카나리 릴리스 적용
- 반복 추가로 인한 구조 퇴화를 막기 위해 피트니스 함수·회귀 자동화를 병행
