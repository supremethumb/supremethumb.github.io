## II. 객체지향 설계의 5대 원칙 (SOLID)

| **구분** | **원칙명 (영문/한글)**                                                 | **상세 설명 및 설계 효과**                                                                                                                   |
| ------ | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **S**  | **SRP**<br>(Single Responsibility Principle)<br>**단일 책임 원칙**    | - [[클래스]](모듈)가 변경되어야 하는 이유는 오직 하나뿐이어야 한다는 원칙<br>- 객체의 책임을 하나로 제한하여 **[[응집도]](Cohesion)를 극대화**하고, 한 책임의 변경이 다른 책임에 미치는 영향을 차단함               |
| **O**  | **OCP**<br>(Open-Closed Principle)<br>**개방-폐쇄 원칙**              | - 시스템의 기능 확장에는 열려(Open) 있어야 하고, 기존 코드의 수정에는 닫혀(Closed) 있어야 한다는 원칙<br>- **다형성과 인터페이스**를 활용하여 기존 코드 변경 없이 새로운 클래스를 추가함으로써 유지보수성을 높임   |
| **L**  | **LSP**<br>(Liskov Substitution Principle)<br>**리스코프 치환 원칙**    | - 자식(하위) 타입은 언제나 자신의 부모(상위) 타입으로 교체될 수 있어야 한다는 원칙<br>- 상속받은 메서드의 규약(사전/사후 조건)을 위반하지 않아야 **다형성이 안전하게 동작**함을 보장함                      |
| **I**  | **[[ISP (Information Strategy Plan)|ISP]]**<br>(Interface Segregation Principle)<br>**인터페이스 분리 원칙** | - 클라이언트는 자신이 사용하지 않는 메서드에 의존하도록 강제되어서는 안 된다는 원칙<br>- 거대한 범용 인터페이스 하나보다, 클라이언트 목적에 맞게 분리된 **구체적이고 작은 인터페이스 여러 개**가 바람직함              |
| **D**  | **DIP**<br>(Dependency Inversion Principle)<br>**의존성 역전 원칙**    | - 고수준 모듈은 저수준 모듈의 구현에 의존해서는 안 되며, 둘 다 **[[추상화]](Interface)**에 의존해야 한다는 원칙<br>- 구체적인 구현 클래스가 아닌 추상화에 의존하게 하여 **[[결합도]](Coupling)를 획기적으로 낮춤** |

## III. 최신 소프트웨어 아키텍처에서의 SOLID 원칙 활용 동향 (2026년 기준)

### 1. 마이크로서비스(MSA) 및 클린 아키텍처(Clean Architecture)의 근간

- [[클라우드 네이티브]] 환경에서 거대한 시스템을 분해할 때, **SRP(단일 책임 원칙)**는 도메인 주도 설계([[DDD (Domain Driven Design)|DDD]])의 바운디드 컨텍스트(Bounded Context) 경계를 나누는 논리적 기준이 됩니다.
- 또한, 비즈니스 핵심 로직이 외부 DB나 프레임워크에 종속되지 않도록 하는 헥사고날(Hexagonal) 아키텍처의 '포트 앤 어댑터(Port & Adapter)' 패턴은 **DIP(의존성 역전 원칙)와 OCP(개방-폐쇄 원칙)**를 아키텍처 레벨로 확장한 가장 대표적인 적용 사례입니다.
### 2. 생성형 AI 코파일럿(Copilot)의 코드 품질 검증 절대 지표

- [[초거대 언어 모델|LLM]]을 활용한 코드 자동 생성이 실무에 전면 도입되면서, "돌아가기만 하는 스파게티 코드" 양산에 대한 우려가 커졌습니다. 이에 따라 2026년 현재 AI [[프롬프트 엔지니어링]] 단계부터 SOLID 원칙 준수를 강제하고, SonarQube 등 CI/CD 파이프라인 정적 분석 도구에 AI가 생성한 코드의 'ISP 위반 여부', 'LSP 위반 여부'를 최우선으로 검열하여 기술 부채를 방어하고 있습니다.
### 3. 멀티 패러다임(함수형 프로그래밍)과의 구조적 융합

- Java, Kotlin, Rust 등 현대 프로그래밍 언어에서 함수형 프로그래밍(FP) 패러다임을 도입하더라도 SOLID 원칙은 유효합니다. 함수 자체가 일급 객체(First-class Citizen)로 다뤄지며, **인터페이스 분리(ISP)와 의존성 역전(DIP)** 원칙은 함수 타입(Function Type)과 고차 함수(Higher-order Function)의 시그니처 설계 규약으로 그대로 계승되어 시스템의 유연성을 보장하고 있습니다.
끝.

## I. SW 재사용성과 유지보수성 향상을 위한 가이드, 객체지향 설계 원칙의 개요

### 가. 객체지향 설계 원칙의 정의

- 객체지향 프로그래밍(OOP) 시 **높은 응집도(High Cohesion)**와 **낮은 결합도(Low Coupling)**를 달성하여 소프트웨어의 **재사용성**과 **유지보수성**을 극대화하기 위한 5가지 설계 지침,. **나. 설계 원칙의 필요성**
- **복잡성 제어**: SW 복잡도 증가에 따른 관리 용이성 확보.
- **변경 용이성**: 요구사항 변경 시 코드 수정의 최소화 (Side Effect 방지),.

### 나. 객체지향 설계 5원칙(SOLID)의 세부 내용,,

| 원칙 (Acronym) | 개념 (Keywords) | 설계 지침 및 효과 |
| --- | --- | --- |
| **1. SRP**(Single Responsibility) | **단일 책임의 원칙**- 클래스는 하나의 책임만 수행 | - **높은 응집도** 추구- 변경 시 파급효과 최소화 |
| **2. OCP**(Open Closed) | **개방 폐쇄의 원칙**- 확장엔 열림, 수정엔 닫힘 | - **Interface** 활용- 기존 코드 변경 없이 기능 추가 |
| **3. LSP**(Liskov Substitution) | **리스코프 치환 원칙**- 자식은 부모를 대체 가능 | - **상속(Inheritance)**의 올바른 사용- [[다형성]] 보장 및 계약 준수 |
| **4. ISP**(Interface Segregation) | **인터페이스 분리 원칙**- 범용보다 구체적 인터페이스 | - 인터페이스의 단일 책임 강조- 불필요한 의존성 제거 |
| **5. DIP**(Dependency Inversion) | **의존성 역전 원칙**- 구체보다 추상화에 의존 | - **의존성 주입(DI)**의 기반- 결합도 감소 및 유연성 확보 |

## III. 객체지향 설계 원칙(SOLID)과 OOP 특징의 관계 및 활용

### 가. 관계 비교,

- **OOP 특징 (캡추다정상):** 객체지향 언어가 가지는 **기술적 특성** (도구).
- **설계 원칙 (SOLID):** 특성을 올바르게 사용하여 좋은 설계를 하기 위한 **가이드라인** (방법). **나. 실무 활용**
- **Spring Framework:** DIP 원칙을 **IoC/DI Container**로 구현하여 객체 간 결합도를 낮춤,.
- **[[Design Pattern (23개 패턴)|Design Pattern]]:** SOLID 원칙을 구체화하여 정립된 검증된 설계 노하우,.
**끝.**
