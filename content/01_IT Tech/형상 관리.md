# 형상 관리 (Configuration Management)

---

## I. 변경을 통제하는 기준선 관리, 형상 관리의 개요

### 가. 정의

- [[SDLC]] 전 과정의 산출물(문서·코드·설정)을 **형상 항목으로 식별하고 변경을 통제·기록·감사하여 무결성과 추적성을 유지**하는 관리 활동 (IEEE 828)

### 나. 필요성

| 구분 | 내용 |
| --- | --- |
| [[무결성]] · 추적성 | 요구사항과 최종 산출물의 일치, 변경 이력 추적 |
| 병행 개발 | 다수 개발자의 동시 수정 충돌 방지 |
| 복구 | 결함 발생 시 승인된 기준선(Baseline)으로 원복 |
| 가시성 | 변경 상태를 이해관계자에게 공유해 통제력 확보 |

---

## II. 형상 관리 절차 및 구성요소

### 가. 형상 관리 절차

```mermaid
flowchart LR
    ID["1. 형상 식별<br/>CI 선정 · 기준선 설정"] --> CT["2. 형상 통제<br/>변경 요청 · CCB 심의"]
    CT --> SA["3. 형상 상태 보고<br/>변경 이력 · 상태 기록"]
    SA --> AU["4. 형상 감사<br/>기능적 · 물리적 감사"]
    CT -- "승인된 변경" --> BL[("기준선 갱신")]
```

- 산출물을 형상 항목(CI)으로 식별해 기준선을 정하고, 변경 요청은 CCB 승인 후 반영하며 그 결과를 기록·감사

### 나. 구성요소

| 구분 | 요소 | 설명 |
| --- | --- | --- |
| 기준 | 형상 항목 (CI) | 관리 대상 최소 단위 (계획서, 설계서, 소스, 테스트 케이스, DB [[스키마]]) |
| | 기준선 (Baseline) | 공식 검토·승인을 거쳐 변경 통제의 기준이 되는 CI 집합 (기능·할당·제품 기준선) |
| 통제 | 변경 요청 (CR) | 변경 사유·영향을 기술한 공식 요청 |
| | CCB | 변경의 타당성·비용·일정을 평가해 승인·반려하는 형상통제위원회 |
| 기록 | 상태 보고 | 작성자·일시·변경 내용·사유를 기록해 추적성 제공 |
| 감사 | 기능적 감사 | CI가 요구된 기능을 충족하는지 검증 |
| | 물리적 감사 | 승인된 변경이 실제 산출물에 모두 반영됐는지 검증 |
| 도구 | [[형상 관리 도구\|버전 관리 도구]] | Git·SVN으로 브랜치·병합·이력 관리 |
| 확장 | 인프라 형상 관리 (IaC) | 서버·네트워크 설정을 코드(Terraform, Ansible)로 형상 통제 |

## III. 비교 및 동향

### 가. 전통적 형상 관리 vs GitOps

| 비교 항목 | 전통적 형상 관리 | GitOps |
| --- | --- | --- |
| 관리 대상 | 문서·소스 코드 중심 | 코드 + 인프라·배포 상태(Manifest) |
| 변경 승인 | CCB 회의 심의 | Pull Request 리뷰·자동 검증 |
| 반영 방식 | 수동 빌드·배포 | 저장소 상태를 클러스터에 자동 동기화 (Pull 방식) |
| 감사 근거 | 변경 관리 대장 | Git 커밋 이력 (SSOT) |

### 나. 동향

- [[쿠버네티스]] 환경에서 Git을 단일 진실 공급원으로 삼는 GitOps(Argo CD, Flux) 확산
- [[SBOM]]으로 외부 구성요소까지 형상 항목으로 관리하는 공급망 관리 강화
- LLM이 PR 요약·충돌 해결·리뷰를 보조
