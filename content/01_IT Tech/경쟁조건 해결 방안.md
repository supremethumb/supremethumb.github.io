# 경쟁조건 해결 방안

---

## I. 실행 순서가 결과를 바꾸는, 경쟁 조건의 개요

### 가. 정의

- **경쟁 조건(Race Condition)**: 둘 이상의 [[프로세스]]·스레드가 공유 자원에 동시에 접근할 때 **실행 순서에 따라 결과가 달라지는 상태**, 공유 자원을 다루는 코드 영역이 임계 구역(Critical Section)

### 나. 임계 구역 해결 3조건

| 구분 | 내용 |
| --- | --- |
| 상호배제 (Mutual Exclusion) | 한 프로세스가 임계 구역에 있으면 다른 프로세스는 진입 불가 |
| 진행 (Progress) | 임계 구역이 비어 있으면 진입하려는 프로세스 중 하나가 유한 시간 내에 진입 |
| 한정 대기 (Bounded Waiting) | 진입 요청 후 다른 프로세스가 먼저 들어가는 횟수에 상한 존재 → 기아 방지 |

### 나. 해결 기술

| 구분 | 요소 | 설명 |
| --- | --- | --- |
| 소프트웨어 | Dekker·Peterson 알고리즘 | 플래그와 차례(turn) 변수로 2개 프로세스 상호배제, 현대 CPU에서는 메모리 순서 재배치 때문에 메모리 배리어 필요 |
| | Bakery 알고리즘 | 번호표로 N개 프로세스 상호배제 (Lamport) |
| 하드웨어 | Test-and-Set·CAS | 읽기·수정·쓰기를 하나의 원자적 명령으로 수행 |
| | 인터럽트 비활성화 | 단일 프로세서 커널에서만 유효 |
| OS·언어 | 뮤텍스 | 소유권이 있는 이진 락, 획득한 스레드만 해제 |
| | [[세마포어]] | 정수 카운터 + P·V 연산, 이진·계수 세마포어 |
| | [[모니터 동기화\|모니터]] | 상호배제를 언어가 자동 보장, 조건 변수로 대기 |
| | [[스핀락]] | 짧은 임계 구역에서 Busy Waiting |
| 비차단 기법 | Lock-free·Wait-free | 락 없이 원자적 연산으로 일관성 유지, Wait-free는 모든 스레드의 유한 단계 완료 보장 |

## III. 비교 및 동향

### 가. 뮤텍스 vs 세마포어 vs 모니터

| 비교 항목 | 뮤텍스 | [[세마포어]] | [[모니터 동기화\|모니터]] |
| --- | --- | --- | --- |
| 형태 | 락 객체 | 정수 변수 + P·V | 언어 구조 (데이터 + 프로시저) |
| 동시 진입 수 | 1 | 카운터 값만큼 | 1 |
| 소유권 | 있음 (획득자만 해제) | 없음 (다른 스레드가 V 가능) | 언어가 관리 |
| 주 용도 | 단일 자원 보호 | 자원 개수 제어, 실행 순서 동기화 (생산자·소비자) | 고수준 동기화 (Java `synchronized`) |

### 나. 동향

- **언어 수준 안전성**: Rust 소유권·`Send`/`Sync` 규칙으로 데이터 레이스를 컴파일 시점에 차단
- **동적 탐지 도구**: ThreadSanitizer(사용자 공간), Linux KCSAN(커널)으로 실행 중 데이터 레이스 검출
- **RCU·락프리 자료구조**: 읽기가 많은 커널 자료구조는 RCU로 읽기 측 락 제거
