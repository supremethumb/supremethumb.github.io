# McCabe 회전 복잡도 (McCabe Cyclomatic Complexity)

## 1. McCabe 회전 복잡도의 개요
- **정의**: 소프트웨어 모듈의 논리적 복잡도를 정량적으로 측정하기 위해, 소스 코드의 제어 흐름도(Control Flow Graph)를 기반으로 계산하는 소프트웨어 복잡도 평가 지표(Metric).
- **목적 및 특징**:
  - **테스트 케이스 도출**: [[화이트박스 테스트]](White Box Test) 시 **기본 경로 테스트(Basis Path Test)**를 수행하기 위한 독립적인 논리 경로의 최대 개수를 도출함.
  - **유지보수성 평가**: 소스 코드의 복잡도를 정량화하여 코드 리뷰 및 리팩토링의 기준으로 활용.
  - **제어 흐름 중심**: 데이터의 흐름보다는 제어 구조(분기, 반복 등)에 초점을 맞추어 측정.

## 2. 회전 복잡도 계산 방법

### 가. 계산 공식
회전 복잡도 $V(G)$는 다음 세 가지 공식 중 하나를 사용하여 동일하게 도출할 수 있습니다.

| 계산 공식 | 설명 | 상세 수식 의미 |
| --- | --- | --- |
| **영역(Region) 수** | $V(G) = \text{면의 수}$ | 제어 흐름도로 분할된 닫힌 면(Region)의 수 + 1 (외부 영역) |
| **노드/간선 기반** | $V(G) = E - N + 2$ | $E$: 간선([[EDGE|Edge]])의 수<br>$N$: 노드(Node)의 수 |
| **조건 분기 기반** | $V(G) = P + 1$ | $P$: 조건 분기 노드(Predicate Node, `if`, `while` 등)의 수 |

### 나. 계산 예시
* IF문과 WHILE문이 각각 1개씩 포함된 모듈의 경우 (조건 분기 노드 $P = 2$)
* $V(G) = 2 + 1 = 3$
* **해석**: 이 모듈을 완전히 테스트하기 위해서는 최소 3개의 독립적인 기본 경로 테스트 케이스가 필요함.

## 3. 회전 복잡도 지표 평가 기준

McCabe는 도출된 복잡도 수치에 따른 모듈의 상태와 위험도 수준을 다음과 같이 제안했습니다. (일반적으로 10 이하를 권장)

| 복잡도 $V(G)$ 수치 | 프로그램 상태 | 위험도 및 조치 방안 |
| --- | --- | --- |
| **1 ~ 10** | 단순한 프로그램 | 테스트 용이, 높은 유지보수성 (권장 수준) |
| **11 ~ 20** | 약간 복잡한 프로그램 | 중간 수준의 위험, 지속적인 모니터링 및 관리 필요 |
| **21 ~ 50** | 복잡한 프로그램 | 구조적 위험성 매우 높음, **리팩토링 적극 권장** |
| **50 초과** | 비구조적 프로그램 | 테스트 및 [[유지보수]] 불가, **모듈 분할(분리) 필수** |

## 4. 실무 활용 방안 및 한계점

### 가. 실무 활용 방안
1. **[[단위 테스트]](Unit Test) 지표**: 분기 커버리지(Branch Coverage) 100% 달성을 목표로 할 때, 필요한 최소 TC(Test Case) 규모를 파악.
2. **코드 리팩토링 지표 (Code Smell 식별)**: CI/CD 파이프라인 정적 분석(SonarQube 등)과 연계하여 $V(G) > 10$인 함수를 경고하고 리팩토링 대상으로 식별.
3. **유지보수 노력(Effort) 예측**: 복잡도가 높은 모듈일수록 버그 발생 확률과 수정 비용이 높으므로 중점 품질 관리 영역으로 선정.

### 나. 한계점 및 보완 대책
1. **데이터 복잡도 미반영**: 변수의 수나 데이터 구조의 복잡성은 배제하고 오직 제어 흐름만 반영함. → *Halstead의 소프트웨어 과학 지표 등과 병행 사용 필요.*
2. **[[객체지향]](OOP) 요소 측정 한계**: 상속, [[다형성]] 등 객체지향적인 설계 특성을 평가하기 어려움. → *Chidamber & Kemerer(C&K) 객체지향 메트릭스 활용.*
3. **단순 코드 길이 무시**: 분기문이 없는 단순 순차 구문은 길이가 아무리 길어도 복잡도가 1로 산정됨. → *LOC(Lines of Code) 지표와 결합하여 종합 판단.*
